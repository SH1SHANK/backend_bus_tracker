# PR Description: Supabase Transport Backend Compatibility & Telemetry Hardening

## Overview
This PR brings the Fastify telemetry ingestion API gateway (`backend_bus_tracker`) into complete structural, cryptographic, and operational alignment with the deployed Supabase transport backend (`NITC_BUS_TRACKING_APP`, migration `20261014040200_complete_transport_backend_foundation.sql`) and the Flutter client.

Branch: `fix/telemetry-supabase-compatibility`  
Base Branch: `stable` (commit `c94ef85`)  

---

## Motivation & Baseline Problems
Prior to this PR, telemetry ingestion was broken end-to-end:
1. **Critical Ingestion RPC Failure (`DB-001`, `DB-002`)**: Fastify called `ingest_telemetry` with 12 parameters including `p_bus_id` and `p_recorded_at`. The deployed RPC is `ingest_telemetry_packet`, which derives `bus_id` dynamically, requires `p_timestamp`, and supports session epochs. Furthermore, Fastify flattened all DB rejections into 401 `device_inactive`.
2. **Cryptographic Incompatibility (`SEC-001`, `SEC-002`)**: Fastify used Node.js `scrypt`, while PostgreSQL functions (`register_tracking_device` and `reset_device_sequence`) use `pgcrypto` Bcrypt (`$2a$08$`). Secrets generated by Fastify failed DB verification, and vice versa.
3. **Hardware Reboot Sequence Lockout (`DATA-001`)**: When an ESP32 hardware tracker rebooted and its sequence counter reset to 1, historical sequence checks permanently rejected all packets as stale because no reset session endpoint or epoch tracking existed.
4. **Pre-Ingestion Duplicate Dropping (`DATA-005`, `CONC-001`)**: Fastify executed an unlocked query to `bus_current_state` and dropped packets in Node memory before invoking Supabase. This bypassed PostgreSQL transaction-scoped advisory locks (`1001` device, `1002` bus), dropped `devices.last_seen` liveness updates, and introduced dirty-read concurrency races.
5. **Contract Mismatches (`DATA-002`, `DATA-003`, `DATA-004`, `API-001`, `API-002`)**: Fastify allowed Kerala-wide coordinates (DB strictly bounds to NITC corridor `[11.200000, 11.450000]`), accepted 6-hour-old packets (DB rejects older than 15 minutes), and called deprecated PostGIS functions.

---

## Architectural Guarantees & Strict Invariants
1. **Zero-Legacy Policy**: Since there are no existing production users, devices, or telemetry rows, no fallback or dual-algorithm compatibility is included. All credentials standardize cleanly on **Bcrypt with 8 salt rounds** (`bcryptjs` in Node, `pgcrypto` `gen_salt('bf', 8)` in PostgreSQL).
2. **16-Character Minimum Secret Invariant**: Consistently enforced at `>= 16` characters across API schemas (`minLength: 16`), database functions, and provisioning scripts (`randomBytes(24)` generating 32-character secrets).
3. **Single Source of Truth**: Fastify acts as an authenticated, validating reverse proxy. Sequence monotonicity, historical deduplication, and atomic updates are handled authoritatively by `ingest_telemetry_packet` under transaction-scoped advisory locks.
4. **Idempotent Reboot Protocol**: ESP32 trackers generate a `session_id` and call `POST /api/v1/auth/reset-session` on boot. If the HTTP response is dropped, retry with the same `session_id` returns the established epoch with `idempotent_retry: true` without incrementing again. Sequence counter resets to `0`, allowing `seq = 1` to be accepted monotonically.
5. **Identifier Mapping**: `devices.id` is the internal UUID primary key. `devices.device_id` is the hardware tracker text ID (e.g. `'NITC-BUS-001'`). Fastify JWT `sub` stores the text ID. `ingest_telemetry_packet(p_device_id text)` takes the text ID, resolves internal UUID for updates, and stores the text ID in `bus_positions` and `bus_current_state`.
